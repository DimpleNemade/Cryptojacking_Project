Evidence-based product and engineering roadmap

Make it useful first.
Make every claim provable.

A critical audit of DimpleNemade/Cryptojacking_Project, its local documentation, GitHub roadmap, implementation, and realistic position among forensic, signature-scanning, runtime, and cloud-security tools.

Professional verdict: the repository is a promising academic artifact-scanning prototype with honest limitations and a cleaner modular core than its initial version. It is not currently an installable CLI product, a memory-forensics tool, a validated cryptojacking detector, or a forensically defensible instrument. The next release should be a narrow alpha—not an “enterprise” platform.

Priority gaps and why they matter

These are the issues most likely to invalidate results, break automation, or make external users distrust the project.

P0 Failed scans still produce a successful process exit

The CLI prints “Analysis complete” and returns 0 whenever report generation finishes, even if the report state is FAILED, PARTIAL, or INTEGRITY_FAILURE. CI and orchestration can therefore treat an unusable analysis as success.

Evidence: cryptojacking_forensics/cli.py:262; report status is not propagated from run_pipeline to main.

P0 The repository contains executable mining software and an archive

The tracked tree includes a roughly 7 MB XMRig executable and a roughly 3 MB archive. Windows security blocked the executable during this audit and the worktree now records it as deleted. Keeping active dual-use binaries in normal Git distribution creates endpoint-alert, contributor-safety, licensing, repository-size, and trust problems.

Evidence: Miner_Samples/xmrig-6.21.0/xmrig, Miner_Samples/xmrig-6.21.0-linux-static-x64.tar.gz.1, and the tracked SHA256SUMS. Do not restore or execute the quarantined file.

P0 The default branch contains a Windows-invalid path named ...

The blob contains stray Volatility error output, not required project material. Its path prevents a normal Windows checkout and is already tracked by GitHub issue #12.

Evidence: root tree entry ..., 719 bytes; GitHub issue #12.

P0 “Memory” input naming overstates the analysis

The program scans file bytes with YARA and GNU strings. It cannot list processes, map addresses, identify sockets, reconstruct execution, or distinguish active mining from a string in documentation. That is artifact scanning, not memory forensics.

Evidence: yara_scanner.py and strings_extractor.py; the project documentation itself acknowledges no OS-aware parsing.

P0 Read-only claims need a narrower, truthful model

Opening one descriptor with rb proves only that one open was read-only. os.access is advisory, platform-dependent, and subject to permissions and time-of-check changes. External engines reopen the path themselves. Software checks cannot establish acquisition provenance, hardware write blocking, or chain of custody.

Revise GitHub issue #13: record observed controls and policy mode; do not label them proof.

P1 Engine resolution and captured output are not bounded

yara and strings are selected from PATH. Their full stdout/stderr are captured in memory and later written, so a large dump or high-match rule can exhaust memory or disk. The timeout is per subprocess, not a total run budget.

Evidence: commands.py:54; three sequential YARA runs plus strings and version probes.

P1 Rule quality is insufficient for severity claims

Rules match generic values such as :3333, :4444, minerd, mining, and xmrig. A single rule match can produce HIGH severity without calibrated likelihood or context. Current correlation depends on whichever match value is retained first.

Evidence: YARA_Rules/network_rules.yar, process_rules.yar, miner_rules.yar, and hard-coded severities in findings.py.

P1 Reports expose sensitive local and evidence-derived data

Absolute paths, commands, YARA values, wallet-shaped strings, and raw strings output are retained. The README warns users, but redaction is manual and output permissions are not hardened.

Evidence: README.md:140 and cli.py:224. Privacy-safe output must be the default, with explicit opt-in for raw data.

P1 Historical test success is not a release gate

The July document records 30 passing tests on one Ubuntu environment. This audit could run CLI help but could not reproduce the suite: the root Python lacks pytest, and the excluded copy's virtual environment references a missing interpreter. Mocked subprocess tests also do not validate real engine behavior across supported hosts.

Evidence: docs/VALIDATION.md; no CI files or package metadata on tracked main.

Recommended vision

An offline evidence-aware triage orchestrator, not a new EDR, SIEM, cloud detector, or memory framework.

The credible wedge is a small CLI that accepts supplied artifacts or structured output from established engines, runs a versioned cryptojacking-focused rule pack, preserves reproducibility metadata, and emits explainable, privacy-aware findings. The value must come from workflow quality and validation evidence—not from pretending broad strings are proprietary detection.

Target CLI contract

A proper CLI is more than an entry point. It is a stable automation contract with safe defaults, inspectable dependencies, bounded execution, and unambiguous terminal states.

$ cj-triage doctor --format json
$ cj-triage rules check --rules ./rules --engine yara-x
$ cj-triage scan artifact ./capture.bin --case CASE-001 --output ./case-output
$ cj-triage scan volatility ./volatility.jsonl --case CASE-001 --format jsonl
$ cj-triage verify ./case-output/manifest.json

Stable terminal states

0 complete/no findings; 10 complete/findings; 20 partial; 30 integrity failure; 64 usage/configuration; 70 internal failure. Final values must be documented and tested.

Output discipline

Machine data on stdout only when requested; progress and diagnostics on stderr. JSON/JSONL validated by schema. Raw strings and absolute paths off by default.

Resource discipline

Explicit total deadline, per-stage deadline, byte limits, match limits, output caps, safe temporary files, atomic finalization, and partial-result markers.

Dependency transparency

doctor reports package, engine, rule-pack, schema, platform, and optional adapter versions without scanning evidence.

Reproducibility

Manifest records input identity, configuration, engine and rule hashes, limits, timestamps, statuses, warnings, and hashes of finalized outputs.

Compatibility

Semantic versioning for the CLI and schema; deprecation window for flags; adapters isolated behind typed interfaces; migration notes for breaking changes.

Metrics that can be defended

Measure defined outcomes with denominators and versioned evidence. Do not use aspirational percentages as facts.

Reliability

Clean-install success by supported OS/Python matrix; end-to-end completion rate by fixture class; deterministic-output rate; bounded-time compliance.

Evidence: CI runs + published environment matrix.

Detection quality

Precision, recall, and error categories on a frozen labeled corpus and a held-out set; per-rule false-positive counts on hard negatives.

Evidence: corpus version, labels, confusion matrix, reviewer notes.

Forensic workflow quality

Hash/control completeness, schema-valid report rate, reproducibility by an independent tester, and documented deviations.

Evidence: known-answer reports and independent test record.

Operator value

Median time to a validated lead versus the user's existing workflow; analyst corrections per run; handoff completeness.

Evidence: timed pilot tasks, not self-reported satisfaction alone.

Adoption signal

External users who repeat the workflow on a second case without developer help; retained pilots; integration requests tied to real work.

Evidence: consented pilot records and follow-up use.

Supply-chain trust

Percent of releases with verified provenance and SBOM; dependency-alert disposition time; reproducible verification success.

Evidence: release attestations and security workflow logs.

Do not build yet

Hosted dashboards, RBAC, a REST platform, automated legal reports, compliance certification, an anonymous threat-sharing consortium, proprietary anomaly scoring, monthly “coverage” promises, or operator certification. None solves the current alpha blockers, and none has validated demand. Revisit only after a reliable CLI is repeatedly used by external analysts.
